# 生产系统重构方案（2026-11-12）

状态：已确认，一次性实施（见第 9 节）。服务端由主会话负责；生产端（`../vocnet-producer`）由一个单独的代理负责。

## 1. 原则

1. **系统覆盖绝大多数情况，不追求 100% 自动化。** 不为少数特例设计复杂的数据结构或逻辑；特例走人工出口，由 Claude 以策展人身份处理。
2. **人工出口必须可靠、便宜。** 任何卡住的工作都要在有限轮次内落到人工处理列表，不能在系统里空转。
3. **在此基础上尽量提高生产效率**，兼顾完整性和质量。
4. **应有尽有。** 关系是本产品的核心卖点：可选项允许“确实没有”，但不允许偷懒跳过。
5. **为分阶段扩展和多语言而设计。** 不怕现在迁移，趁数据量还小把结构理顺。

## 2. 词条与主词

### 2.1 主词名单（新）
- **名单是导入的数据，不由 worker 新建。** 每个主词记下来源（如 CEFR、词频表、词典词表）和批次号。
- **导入一批，系统就为新主词建好词条和待办**，生产端下次领任务时自动接着做，不需要改代码。
- **导入时统一去重：**
  - 原形已经收录的跳过；
  - 变形还原成原形，比如 coming 归到 come；词典词表里本身单列的词（left、saw、found）照常收录；
  - 拼写变体合并成一个词条，另一种写法作为变体词形，比如 colour 和 color。
- **分批计划（每批导入前先算出名单，确认后再导入）：**

| 批次 | 范围 | 规模 |
|---|---|---|
| 1 | CEFR 词表全部 | 8,855 个，已全部有词条，标成主词即可 |
| 2 | 词频 Zipf ≥ 4，还原成原形后去掉已有的 | 估计几千个 |
| 3 | 词频 Zipf ≥ 3.5 | 估计再增加几千个 |
| 4 起 | 完整的词典原形词表（WordNet / Wiktionary 等），逐步收全 | 几万个 |

### 2.2 短语
- **短语是独立的词条**，有自己的义项、译词、例句和关系。
- **归属用主词身上的一条明确事实来记录**（新的事实类型，暂名 `phrases`）：列出挂在这个主词名下的短语词条。一个短语可以同时挂在多个主词下面，比如 in front of 挂在 front 下面。现在按“以这个词开头、并且有动词义项”推算归属的方式（`server/adapters/repos/nodes.ts:388`）删除。
- **收录标准，不设数量上限：** 学习词典把它当作这个主词的短语或习语收录，或者它的意思不是字面意思的简单相加、是一个固定说法。不挂在任何主词下面的字面组合（white rice、paper handkerchief）不收。
- **短语由主词的“短语”工作新建。** 以后新加了主词，它名下的短语也会自动补上。
- **审核：** `phrases` 事实由 Jev 对每个短语逐个提问，再交给 LLM 审。
- **排队：** 短语词条跟着它的主词排队。

### 2.3 worker 不再新建词条
- **关系只能连到已收录的词条。** 找不到目标词，就在工作记录里用结构化的字段记下缺了哪个词（不只是写在说明里）；这些记录汇总成“下一批候选名单”。
- **需要补收某个词：** 生成一个缺词 ticket，由策展人决定（见第 7 节）。
- **新的一批主词导入后**，系统查出哪些工作记录缺的正是这批词，把对应的关系项重新开放，worker 自然会补上。

### 2.4 迁移：现有 10,489 个 worker 自建的词条
- **在 CEFR 词表里的：** 转成第 1 批主词。
- **符合标准的短语：** 保留，写进对应主词的 `phrases` 事实。
- **其余的（变形、不属于任何主词的字面组合等）：** 删除，挂在它们上面的关系也一起删除，目标词记成下一批候选。
- **拼写变体合并：** 保留常用写法的词条，另一个词条里重复的事实删掉，它的拼写改成变体词形。
- **准入审核里的特例规则**（已记录的变形、复审等，`docs/design.md` 中 Entry admission / Recorded inflections 一节）随之删除。

## 3. 事实模型

### 3.1 现状与调整

| 事实类型 | 调整 |
|---|---|
| `entry` | 保留 |
| `sense` + `sense_list` | **合并成“义项清单”**（见 3.2） |
| `form` | 保留；要不要合成一张变化表，等审核成本数据出来再定 |
| `relation` | 保留 |
| `pronunciation`、`syllables` | 保留 |
| `example` | **去掉里面的 `translations`**，只保留原文 |
| `translation` | **改成“每个被翻译的内容、每种语言一条”**（见 3.3） |
| `topic` | 保留；要不要合成每个义项一条，待定 |
| `grammar` | 保留，改为可选项 |
| `morphology` | 保留 |
| `collocation` | 保留，原文中的翻译拆到翻译事实里 |
| `gap_closure` | **删除**（见 3.4） |
| `phrases`（新） | 主词名下的短语列表（见 2.2） |

feedback（用户反馈）不是事实，但它的处理流程改为生成 ticket（见第 7 节）。

### 3.2 义项清单
- **一个词条只有一条清单：** 列出全部义项，每个义项包括词性、释义、语域、地区，并分成“常用”和“其他”两组排好序。义项 ID 照旧保留，供关系、例句、翻译等引用。
- **只有义项工作能提交清单。** 一次提交、一次审完。
- **清单发布前允许临时义项：** 其他工作为了建关系，可以先临时新建义项。做清单的 worker 能看到这些临时义项及挂在上面的关系，必须逐个表态：收进清单，或者删掉。删掉的话，挂在上面的关系也一起失效。
- **清单发布后，worker 不能再新建或删除义项**，只能引用。要修改只能由策展人改；涉及义项的问题都以 ticket 的形式交给策展人。
- **审核：** Jev 对每条释义逐条提问（一次调用就能问完）；LLM 再审整份清单。
- **迁移：** 现有 45,867 个义项和 16,680 个义项列表，按词条合并成清单。没有列表的词条，用现有生效义项生成一条，并标为待审。

### 3.3 翻译
- **每个被翻译的内容、每种语言一条事实：** 比如 `{ language: "zh", target: <义项 | 例句 | 搭配>, text }`。
- **要翻译的内容：** 先做义项译词、例句、搭配三样。
- **翻译工作：** 一个词条、一种语言一项，一次把这个词条里需要翻译的内容全部翻完，但每条翻译分别存储、分别审核。
- **加新语言：** 只需要为每个词条新增那种语言的翻译工作，原有事实都不用动。
- **原文被修正（替换）后**，翻译引用的原文 ID 不再生效，旧翻译就不再显示（可见性在读取时推算），同时重新开放翻译工作。原文那条事实不受影响。
- **必填：** 在每种已开放的语言下，义项译词、例句翻译和搭配翻译都属于必填项。
- **迁移：** 现有 15,421 条义项翻译改成新格式；26,418 条例句里的中文拆成独立的翻译事实。拆完之后，例句不会再因为加翻译而被整条替换（过去已经因此替换了 7,073 次）。

### 3.4 删除 gap_closure，区分必填项和可选项
- **必填项：** 义项清单、义项译词、例句、发音、音节、构词，以及有变化的词的词形。必须有内容才算完成。
- **可选项：** 同义词、反义词、上位词、组成部分、搭配、短语、词族、话题、语法。做过一轮就算完成。
- **做过一轮但没找到：** 必须在工作记录里写一句说明（考虑过哪些、为什么不是），不产生事实，也不送审。这样的项会拉低可信度（见第 6 节），进入抽查。
- **迁移：** 现有 13,284 条 gap_closure 转成工作记录（“已做过一轮，空着，附原理由”），然后删除这个事实类型、它的审核规则和相关代码。

## 4. 审核

### 4.1 审核链固定为一次性
- **决策模型通过就直接放行；没通过或拿不准，交给 LLM，LLM 给出最终结论。**
- **决策模型只用两个：Jev 和 OpenAI Decisions（gpt-6-luna）。** d3、flint 不采用。
- **去掉现有的两个例外：** 上位词、组成部分在 Jev 通过后仍要再过一遍 LLM；关系在 Jev 打分低于 0.5 时直接拒、不交给 LLM。
- **上位词和组成部分的风险：** 当初加例外，是因为 Jev 高分放行了 dog → canine 这类挂到生物学分类上的上位词（`docs/design.md:350–361`）。这次的做法是把规则写进 Jev 的问题；切换之前，先用验证程序在快照数据上确认改写后的问题能拦住这类错误，不分阶段上线。

### 4.2 每类事实由谁审
依据：`/private/tmp/claude-501/jev-eval/REPORT.md`、`/private/tmp/claude-501/model-eval/decisions/REPORT.md`。这些是小样本结论，所以切换之前，先用验证程序在快照数据的自然比例样本上确认每个门槛。

每类事实各自定放行门槛，先按评测结果填，以后按抽查结果调：

| 类型 | 审核方式 | 放行门槛（初值） |
|---|---|---|
| 词条、义项、词形、关系、语法 | Jev 先审 | 0.8 |
| 反义词 | Jev 先审 | 0.9 |
| 构词 | 改成 Jev 先审（问题里写入“按现代英语构词、不按词源”的规则） | 0.8 |
| 翻译 | Jev 和 luna 任一达到门槛就放行 | 0.8 |
| 话题 | Jev 和 luna 的平均分达到门槛就放行 | 0.8 |
| 音节 | luna 先审 | 0.9 |
| 例句、搭配、发音、义项清单、短语列表 | 只交给 LLM（短语列表先由 Jev 逐个提问） | — |

- **Jev 的问题统一改写：** 把审核规则里通过和不通过的条件原样写进问题，事实数据放进背景信息（state）里。
- **外部依赖：** luna 走 OpenAI 直连，网络或额度出问题时必须当成重试，不能变成审核结论。

### 4.3 每项工作最多做 2 轮
- **一项工作最多做 2 轮：** 第一次，加上一次带着审核意见的重试。依据：第 2 轮的成功率是 45%，第 3 轮只有 36%。
- **有没有进展，只看已填的项数是否真的增加了。** 撤回再恢复、换个说法再交，都算没有进展。现在的判断方式（`server/domain/work.ts:933`）是看缺口内容有没有变，会被死循环清零，这次一并修掉。
- **第 2 轮还没成功，就生成一个 ticket，转给策展人。**
- **原样重复提交被拒过的内容，直接退回，并计作一次没有进展，不再送审。**（consist + -ent 被拒过 625 次）

## 5. 工作流

1. **出口：** 见 4.3。
2. **排序：** 先按主词批次，同一批内再按阶段、级别、词频排。
3. **只有义项工作能新建或撤回义项**（由 3.2 保证）。这样今天出现的 7 起扯皮（underground、gender、deal out、labour、self-destruction、forget it、sex）都不会再发生。

## 6. 完成度与可信度

- **完成度：** 必填项有内容、可选项做过一轮，才算完成。
- **可信度（取代现在的“质量”）：每条事实的可信度，等于“这类事实走这条审核路径时的实际正确率”。** 词条的可信度取它全部事实里最低的一个。
  - **审核路径：** 策展人确认；决策模型直接放行；两个模型都同意；决策模型拿不准、由 LLM 判定；只经过 LLM；重试后才通过。
  - **可选项做过但空着的：** 也算一种路径，有它自己的正确率（“确实没有”的比例）。
  - **正确率表：** 按“事实类型 × 审核路径”维护一张表，先用评测结果填，再由抽查持续更新。这样不同类型、不同路径之间能拉开差距，计算上也只是查表。
- **用途：** 筛选抽查对象。按“可信度低 × 词频高”排序，从最前面开始抽查，抽中的生成 ticket。
- **控制台：** 显示“完成度”和“可信度”两个分数，替换现在恒为 100% 的“质量”。

## 7. 人工出口：ticket

- **所有需要人工处理的东西，统一成 ticket：** 一个 ticket 包含类型、对象（词条、义项或事实）、原因、状态（待处理 / 已处理）、处理人和处理记录。
- **ticket 的来源：**
  - 工作做满 2 轮还没成功（4.3）；
  - 用户提交的反馈；
  - 抽查选出的低可信度事实（6）；
  - 建关系时缺的词（2.3）。
- **删除 feedback 循环：** feedback worker 及其相关逻辑全部删除，用户反馈直接生成 ticket，和生产中的人工处理走同一套流程。
- **处理：** 策展人按 ticket 逐个处理：修正事实、补收词条，或者确认没问题后关闭。策展人可以修改已定下的义项清单，以及任何事实。
- **控制台：** 现在的“人工处理”页面改成 ticket 列表。
- **迁移：** 现有的人工处理项（work/curation）和用户反馈，转成 ticket。

## 8. 运维

- **生产环境就在主仓库里跑，不开 worktree。** 并行开发的 worktree 由仓库所有者自己开。
- **不做备用审核器。**
- **策展人密钥、日志、备份移出 `/private/tmp`**，放到固定位置；日志定期清理；加上磁盘空间监控。
- **代理统一用 `hc` 调度。** 需要长时间运行的，加 `--outlive-parent`。

## 9. 执行方式：一次性改到位

- **一次性完成，不分阶段上线：** 本方案的全部内容（第 2–8 节）一起实现、一起迁移，全部完成后才重新启动生产。代码可以分多次提交到本地 main，但中途不重启生产来试。
- **不确定的地方，单独写验证程序：** 比如 4.1 的上位词问题、4.2 的各类门槛、迁移规则的影响范围，都在数据库快照上验证，而不是靠上线后迭代。
- **分工：**
  - **服务端（本仓库）：** 主会话负责，包括领域规则、接口、迁移、控制台、`docs/design.md` 和 `spec/*.feature`。
  - **生产端（`../vocnet-producer`）：** 一个单独的代理负责，按服务端定下的新接口改 worker 的工具和提示词，删除 feedback 循环。
  - **最后两边联调。**
- **对外接口和控制台：** 随事实模型一起改（义项清单、翻译、短语、ticket、完成度和可信度），对外字段名用 snake_case。
- **数据：**
  - 迁移前先备份数据库，备份放到 `/private/tmp` 以外的固定位置；
  - 迁移脚本先在快照上跑通，统计影响范围，再在正式数据上执行；
  - 顺带清理没有意义的数据。
- **完成标准：**
  - `pnpm verify` 通过；
  - 迁移后数据一致性检查通过，包括引用、义项清单、翻译、短语归属；
  - 生产端和服务端联调通过；
  - 重新启动生产，跑一轮观察正常。
- **进展汇报：** 每 30 分钟汇报一次。
